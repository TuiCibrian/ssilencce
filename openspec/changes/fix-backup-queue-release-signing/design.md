## Context

See proposal.md - Why. Current state that shapes the approach: restore previously validated declared ZIP sizes that a `ZipInputStream` cannot provide (streamed entries declare -1), so it aborted every archive; backup creation closed the archive after the lyrics entry; the lyrics cache model had no serializer; queue rows were keyed by media id; the saved shuffle order was discarded whenever filtering unavailable items shrank the restored queue; Release signing fell back to the debug keystore silently. The project builds with the Gradle configuration cache enabled (`org.gradle.configuration-cache=true`), has no test source sets, and CI (`android.yml`) runs `lint ktlintCheck` without a keystore (including Release lint variants).

## Goals / Non-Goals

**Goals:**
- Backup archives round-trip on the device: create repeatedly, restore selectively, reject oversized/unsafe archives with a bounded, cancellable reader.
- Queue contents (including duplicates) and the saved shuffle order survive process restarts, with a lossless migration of existing databases.
- Release packaging cannot silently ship a debug-signed artifact; local development flows stay usable.
- Honest diagnosis: creation/restore failures are logged and toasted, never silently swallowed.

**Non-Goals:**
- Automatic backups (tracked separately in `add-scheduled-backups`).
- Multiple named queues or queue-local search (tracked in `add-named-queues`).
- Cryptographic authenticity/signature verification of archives; verification is structural and content-based.
- Changing the ZIP format, file extension or entry naming scheme.
- Adding test source sets or dependencies.

## Decisions

- **Count actual bytes instead of declared sizes.** A private `BoundedEntryInputStream` view wraps the `ZipInputStream`, resets per-entry counters at each `nextEntry`, and throws `IOException` when a lyrics entry exceeds 10 MB, any entry exceeds 100 MB, or the total exceeds 100 MB; the 1000-entry cap stays in the loop. Alternative considered: parse the central directory via `ZipFile` for declared sizes — rejected because it needs a seekable copy of the SAF stream.
- **Never wrap the archive in a closing writer.** The lyrics JSON is written with `out.write(bytes)` plus `closeEntry()`; no `BufferedWriter.close()` can finalize the archive mid-entries.
- **Cancellation-aware I/O.** `currentCoroutineContext().ensureActive()` per entry/line and a chunked `copyToWithCancellation`; `CancellationException` is rethrown, not toasted, so structured concurrency is preserved.
- **Path safety by basename validation.** Restored files use only the entry basename; `requireSafeFileName()` rejects empty, `.`, `..`, and names containing `/` or `\`.
- **`@Serializable` on `LyricsEntity`.** Kotlinx serialization generates `LyricsEntity$$serializer`, so `getLyricsZipItems` (encode) and `restoreLyrics` (decode) work. Defaults are omitted when encoding (`instrumental = false`), which decode restores; verified against the compiled serializer.
- **Queue identity = position.** `QueueEntity` keys on `order`; `replaceQueue` clears and re-inserts in one `@Transaction`, so repeated media ids persist. Alternative considered: composite key or auto-increment id — position is the honest identity and needs no additional column. Room v7 migration creates the new table with `PRIMARY KEY(\`order\`)`, copies `INSERT OR REPLACE ... ORDER BY \`order\``, drops and renames.
- **Resume position after a shrunk queue maps by occurrence.** When filtering drops unavailable songs, one lockstep walk over the saved and restored lists builds `savedToRestored` (saved position → restored position, or -1), so repeated songs resume at the right occurrence instead of a first-id or distance heuristic. A surviving current occurrence keeps its saved position-in-track; a missing one resumes at the item that took its place, clamped into range, with position-in-track reset to 0. The same map feeds the shuffle-order remap.
- **Shuffle order is compacted, not discarded, on restore.** `SerializedOrder.remap(savedToRestored)` filters the saved permutation to surviving positions and renumbers it, preserving the relative shuffled sequence exactly as `ImprovedShuffleOrder.cloneAndRemove` does for live removals. The payload is accepted only when both the saved order and the restored mapping are complete permutations of their domains. A legacy seed-only `data == null` payload is regenerated from the seed at the restored length; a missing saved order keeps the previous `UnshuffledShuffleOrder` fallback. An undecodable payload sets a decode-failure flag, clears `SHUFFLE_ORDER`, and yields no order; a decodable but invalid payload for a non-empty queue (wrong length, duplicate/out-of-range index, failed remap) also clears it. Both leave `shuffleOrder` null, so shuffle is disabled for that restored session while the queue remains intact. An empty restored queue preserves the previous behavior: an absent order uses `UnshuffledShuffleOrder(0)`, an empty valid order keeps shuffle enabled, and an inconsistent non-empty order falls back to null safely. The restored queue is never emptied because of a bad shuffle order. Alternative considered: repeated `cloneAndRemove` calls per missing range — correct but O(N × ranges), rejected for large queues.
- **Missing-item removal uses timeline indices and a validated snapshot.** Live cleanup in `PlayerViewModel` marks unavailable items by `QueueItem.second` (timeline/window index), groups consecutive timeline indices, and removes the ranges in descending order. Shuffle changes the queue-list order but not the timeline-index domain consumed by `removeMediaItems`; using list positions would remove unrelated tracks when shuffle is enabled. The pass captures one `queueTimeline` snapshot before reading `queueItems`, sizes the missing-index array from it, and on Main revalidates `player.currentTimeline === queueTimeline` plus `player.mediaItemCount == queueTimeline.windowCount`. A stale pass removes nothing and returns from the locked block before publishing `_queueFlow`/`_positionFlow`, leaving the queued timeline-event pass to rebuild from the new snapshot. Shuffle-off behavior is unchanged because the domains coincide; non-removal passes retain their pre-existing transient flow-publication behavior.
- **Signing guard with two layers.** A `releaseUnconfigured` signing config pointing at the missing root `keystore.properties` fails `validateSigning*Release` on any packaging path (mechanical backstop, configuration-cache safe); a `taskGraph.whenReady` guard refuses `assemble*Release` / `bundle*Release` / `install*Release` early with instructions, unless `-PallowDebugSigning=true` / `SSILENCCE_ALLOW_DEBUG_SIGNING=true`. Lint/intermediates are not matched, so `lint`/`ktlintCheck` CI stays green; CI tag releases keep injecting `keystore.properties` from secrets.
- **Logging on swallow points.** `Log.e("BackupHelper", ...)` on the three catch-alls; user-facing toasts unchanged.
- **Structural restore verification.** `restoreBackup` counts ZIP entries, recognized entries and content entries actually imported. Zero entries throws (empty or non-ZIP stream); a non-empty archive with zero entries matching the selected content reports a warning; a matching entry that yields zero imported rows/files reports a warning. Success is announced only when at least one selected content item was actually restored. The counters live in a small pure `RestoreSummary` helper so they can be exercised without an Android runtime, while the final toast decision remains in `BackupHelper`.

## Risks / Trade-offs

- [Streamed entries are read fully even when a content type is not selected] → unselected and unrecognized entries are explicitly drained through the counting stream (per-chunk `ensureActive`), so their actual bytes count towards the per-entry/total limits and cancellation stays responsive; drained-after-handler reads return immediately (probe-verified). `ZipInputStream.nextEntry` would otherwise inflate them unaccounted (review finding, fixed 2026-10-16).
- [Full queue rewrite per debounced save] → writes stay inside one transaction and are debounced at 500 ms; row counts are modest even for large queues.
- [Migration on very old databases with duplicate orders] → `INSERT OR REPLACE ... ORDER BY \`order\`` keeps the last row per position; pre-existing data could not hold duplicates anyway (media-id key).
- [Corrupt or stale shuffle payload] → payloads are validated as permutations against the saved/restored mapping; undecodable data and invalid data for non-empty queues clear `shuffle_order` and disable shuffle for the restored session while keeping the restored queue, so a bad order cannot trigger the restore catch-all that dispatches an empty queue. An inconsistent non-empty order on an empty queue falls back to null without applying it.
- [Timeline changes between queue capture and missing-item removal] → the removal pass captures one `queueTimeline` snapshot before reading `queueItems`, sizes the missing-index array from it, and revalidates timeline identity and `mediaItemCount == windowCount` on Main immediately before removing. A stale pass abandons its removals and returns from the locked block before publishing `_queueFlow`/`_positionFlow`, so the queued timeline-event pass retries from the new snapshot. Non-removal passes are not covered by this guard and retain their pre-existing transient flow-publication behavior.
- [Guard bypass via unusual task names] → the mechanical `validateSigning*Release` backstop covers direct `package*Release` invocations; abbreviations and aggregates resolve into the guarded names.
- [Physical-device acceptance not covered] → release frame-timing/battery remains open (task 4.4) because only an emulator is available; documented in verification notes.

## Migration Plan

1. Ship Room v7 with `MIGRATION_6_7`; existing installs migrate on first open (verified on `com.ssilencce.debug` with a real v6 database; rows `22,21,19,20` preserved, `user_version` 6 → 7, `PRIMARY KEY(\`order\`)`).
2. Rollback: keep the database file; the migration is additive to row contents. No backup-format migration needed (no legacy lyric JSON could have been produced because encoding throws without the serializer).
3. Distribution: release builds require `keystore.properties` (or the explicit non-production opt-in); CI keeps injecting it from repository secrets.
